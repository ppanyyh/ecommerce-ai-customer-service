# PORTFOLIO.md — 作品集说明

> 项目：电商客服AI助手 V3.2.2（个人作品集原型，模拟数据，非生产系统）

## 1. 我解决的问题

电商售后客服有三类问题靠"检索+生成"很难直接做好：

1. **风险问题不能自由发挥**——用户要求"保证三天内到货""赔我一台新的"，任何模型幻觉式的应答都是商业事故；
2. **订单是精确数据不是语义问题**——"订单 202609180002 到哪了"必须查结构化数据，用向量相似度找"最像的订单"必然串单；
3. **服务必须永远可用**——LLM 服务不可用时客服不能瘫痪。

我构建了一个把这三件事都工程化的客服后端：混合检索负责"找到对的资料"，结构化订单路由负责"查准数据"，风险下限机制负责"守住安全边界"，本地降级负责"永远有回应"。

## 2. 为什么使用混合检索

项目做过一次严格的对比实验：纯向量基线下，20 条检索评测中**规则类 Hit@1 = 0%**——规则片段（如"超范围承诺需转人工"）的语义表达与 FAQ 高度竞争，Top1 总是被"更口语化"的 FAQ 占据，而 Recall@3 有 94.1%，说明正确片段其实在 Top3 里。

关键词检索正好互补：规则的别名、型号、数字等信息关键词可以精确命中。最终采用 RRF（K=60）等权重融合，不调排序权重（冻结在清单里），开发集阶段 Answer Hit@1 达 90.2%。盲测下降到 54.5%——这个泛化落差是本项目最重要的教训之一（见第 10 节）。

## 3. 为什么订单不进入向量库

三个原因：

- **正确性**：订单查询是精确匹配问题（12 位单号 → 唯一记录）。向量检索返回"最相似"的记录，语义上"202609180002"和"202609180003"几乎一样，任何 embedding 空间里的邻近都会导致串单；
- **隐私**：向量库是全局语料，订单内容（收件人、地址、电话）一旦入库就可能被无关 query 相似度召回。结构化直查保证"只有完整单号+本人语境才能取数"；
- **事实性**：订单回答只允许展示允许字段（状态/商品/数量/金额/物流），且禁止编造预计送达和退款时间——模板化生成比 LLM 生成更可控。

盲测中订单路由/事实准确率 87.5%（7/8），唯一失败是"尾号 003"这类部分指代不识别——是意图覆盖问题，不是架构问题。

## 4. 为什么风险判断不能完全交给大模型

三个理由：

1. **召回确定性**：LLM 对"我要个说法""这事没完"这类中文施压表达的敏感度不稳定，而风险规则是有限集合（8 条），可以用结构化检测器（对象+动作+状态+语境）做确定性召回，再叠加关键词表兜底；
2. **等级不可协商**：规则等级（HR-01~08）来自业务口径，必须"模型与本地结果只能抬高、不能降低规则风险"（risk floor 机制，`risk_levels.py` 唯一定义）。纯 LLM 判断无法提供这种"下限保证"；
3. **可审计**：每条风险触发都能回溯到规则 ID、意图证据和等级依据，出了问题可以定位；黑盒模型判断做不到。

代价是词表覆盖问题会在口语改述下暴露——盲测中 HR-07/HR-08 各有 2 条新表述漏检，这正是"规则式方法+泛化能力"的权衡实证。

## 5. 如何避免内部规则泄露

四层防线：

1. **数据层**：规则片段做 index/display 拆分——检索用 `retrieval_text`，返回给生成环节的是原始文本，且 RULE 片段原文在本地组稿时被过滤；
2. **提示词层**：System Prompt 明确禁止 answer 出现规则编号（HR-xx/FAQ-xxx）、"知识库"、"现有资料未覆盖"等内部用语；
3. **校验层**：DeepSeek 返回后做内部术语正则检查 → 命中重试一次 → 仍命中替换为安全模板；本地降级模板同样过过滤器；
4. **评测层**：盲测含 14 个内部泄漏扫描点（HR 编号、SOP、scope 标签、force_handoff、RRF、相似度、阈值等），**最终结果泄漏 = 0**。

## 6. 如何设计开发集和盲测集

- **开发集**（V3.2 100 条 + V3.2.1 80 条）：用于调优，覆盖每类能力的正反例（如 HR-07 的"真正承诺/否定/双重否定"三形态），允许迭代；
- **盲测集 v3**（80 条）：**全新问题**，禁止复制旧 query、禁止同义改写、禁止按关键词表反向拼题；要求自然口语、错别字、省略、多意图；对 1250 条历史查询黑名单做 n-gram/LCS 查重（24 项自动校验 + 28 条人工抽查）；
- **标注先于运行**：每条用例的期望片段、规则、风险等级、handoff 在执行前冻结；16 项目标先于结果写入 manifest。

## 7. 为什么 blind 只能执行一次

如果盲测可以反复跑，它就退化成了又一个开发集——"针对失败案例修复→重跑→通过"的循环会让指标失去泛化意义。所以：

- 评测器带 `--execute-once` 显式门控，无参数拒绝执行；
- 执行清单记录 `execution_count=1`、`retries=0`；
- 盲测结果无论好坏**只归档不修复**（本项目最终盲测 Hit@1 54.5% 未达标，依然如实发布）。

这套纪律模拟的是真实生产环境中"上线前的最后一次验收"：你只有一次机会。

## 8. V3.0 到 V3.2.2 的关键变化

| 版本 | 核心变化 | 解决的问题 |
|---|---|---|
| V3.0 | Chroma + bge-small-zh 向量检索 | 纯关键词的语义召回缺口 |
| V3.1 | 门控三分类 + 独立盲测纪律 | 无关问题误命中、评测污染 |
| V3.2 | 业务感知混合检索 v2 + 风险意图结构化 + 本地降级组稿 | 风险泛化、LLM 不可用时的服务连续性 |
| V3.2.1 | 未知商品识别、复合价格意图、否定守卫、订单本地回答、分风险转人工文案 | 服务实测暴露的 6 类业务缺陷 |
| V3.2.2 | `risk_levels.py` 统一风险等级（修复 adapter 反序根因）、版本标识、最终冻结 | 风险等级被错误降低的系统性 bug |

## 9. 最终成功部分

- **工程与安全面全部达标**：80/80 一次执行、0 异常 0 重试、内部泄漏 0、禁止承诺违规 0、irrelevant 误放行 0%、wrong handoff 8.8%、P95 42.4ms、DeepSeek 0 次（纯本地降级完成全部评测）；
- **商品/FAQ 检索强**：Hit@1 分别 87.5% / 90%，scope 准确率 94.3%；
- **过程资产完整可审计**：候选冻结/盲测冻结/执行清单/归档清单四级 SHA-256 留痕，任何人可复现验证链条。

## 10. 最终失败部分（如实呈现）

- **总体 Hit@1 54.5%**（目标 85%）、union Hit@3 81.8%（目标 95%）——开发集 90.2% 到盲测的落差证明存在对开发集表达方式的过拟合；
- **unsupported 误放行 20%**（2 条商品串答：问音箱估价返回台灯资料）；
- **high-risk handoff 76.5%**、risk floor 符合率 77.1%——风险意图在全新口语表述下漏检；
- **B 层 FAQ 串答 2 条**（最严重缺陷：复合价格问题返回退货 FAQ）；
- Rule Recall@3 69%、HR-08 片段召回 0%（风险意图正确但片段语义距离大）。

这些失败**未做任何修复**——按既定纪律，盲测后不再改代码，失败清单作为后续版本输入归档。

## 11. 如果进入生产环境还需要什么

1. 真实数据源（商品中心/订单中心 API）与缓存策略，替代模拟数据；
2. 用户身份鉴权与"仅可查询本人订单"的强校验（当前只做了意图级防护）；
3. CORS 收紧、HTTPS、限流、审计日志；
4. 会话与工单持久化、人工坐席工作台与转工单闭环；
5. 持续评测管线：线上 badcase 自动回流 → 新盲测集定期重建（而非固定一套）；
6. 针对盲测暴露的 7 类失败模式修复后，用**全新的**盲测集重新验收；
7. 多轮对话与上下文管理。

## 12. AI在开发中的参与方式

- **AI 生成**：后端代码（FastAPI/检索器/评测器/测试脚本）、知识库初稿、文档初稿、修复实现——由 AI 智能体在分阶段指令下产出，全程约数十轮"指令→实现→回归→报告"循环；
- **AI 也会犯错**：本项目记录了 AI 引入并被人类验收拦下的真实缺陷（风险排序反序、否定守卫漏判、评测器把 `message` 误列入响应字段等），说明**无人工验收的 AI 代码不可信**。

## 13. 本人负责的决策与验收工作

- **业务口径**：5 类问题分类、风险是独立维度、8 条规则等级、哪些问题必须转人工、"否定承诺不算承诺要求"等裁定；
- **评测纪律**：确立"baseline 先行、冻结后测、盲测一次性执行、禁止回看调优"的规则并在每阶段强制执行（哈希校验、状态校验、执行前 24 项检查）；
- **验收把关**：每阶段人工复核 AI 产出（如发现 V3.2.1 报告"269/309"系笔误、识别评测器口径误报、抽查盲测标注与规则等级冲突）；
- **停止决策**：盲测未达标后选择"如实归档、进入作品集整理"而非继续修复刷分——这个决策本身就是对评测纪律的坚持。
