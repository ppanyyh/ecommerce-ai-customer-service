# INTERVIEW_GUIDE.md — 面试讲解稿

> 项目：电商客服AI助手 V3.2.2（个人作品集原型）。所有指标引自 `backend/data/final_blind_v3_eval_report.md`，未修饰。

## 一、30秒项目介绍

"我做了一个电商售后客服 AI 后端原型：混合检索（关键词 RRF + 向量）加结构化订单直查，配一套风险下限机制——规则触发的风险等级模型只能抬高不能降低，高风险自动转人工；DeepSeek 不可用时自动降级到本地模板，服务永远可用。最重视的是评测纪律：盲测集冻结后只允许执行一次，最终结果包括未达标的 Hit@1 54.5% 全部如实归档。"

## 二、2分钟项目介绍

要点顺序：业务场景（售后客服三大难点：风险、订单精确性、可用性）→ 架构（FastAPI + query analyzer 门控 + 混合检索 + 订单路由 + 风险下限 + 本地降级）→ 评测方法（开发集→validation→候选冻结→80 条盲测一次性执行，1250 条历史查询黑名单查重）→ 结果（工程与安全面全达标：泄漏 0/违规 0/P95 42.4ms；检索面如实暴露泛化落差：开发集 Hit@1 90.2% → 盲测 54.5%）→ 最大收获（过拟合教训 + 无验收的 AI 代码不可信）。

## 三、5分钟架构讲解

按数据流讲：

1. **入口**：FastAPI `/api/chat`，Pydantic 校验；
2. **分流**：V3 适配器先判订单——12 位订单号走结构化直查（不进向量库），否则进检索；
3. **理解**：query_analyzer 做门控三分类（supported/unsupported_business/irrelevant）+ 意图识别（显式商品编号、未知商品、复合价格、承诺类、服务时间）；
4. **检索**：关键词（别名/型号/数字增强）与向量（Chroma + bge-small-zh-v1.5）并行召回，RRF K=60 融合，规则安全网补充；规则片段做 index/display 拆分，检索语义与展示文本分离；
5. **风险**：结构化意图检测器（risk_intents）+ 关键词风险表 → `risk_levels.py` 统一等级 → 风险下限（模型只能抬高不能降低）→ 类型化转人工文案；
6. **生成**：DeepSeek 可用则生成并做内部术语检查（命中→重试→安全模板）；不可用则 `compose_local_answer` 本地组稿；
7. **响应**：八字段（category/answer/sources/risk_level/handoff_required/handoff_reason/answer_mode/risk_decision）。

## 四、一次请求完整链路（举例）

用户问"收到的耳机左边没声音"：

```
POST /api/chat
→ 非订单号 → query_analyzer：售后语境 + 故障表达
→ 混合检索：向量召回 FAQ/商品片段；risk_intents 命中 HR-08（到货即损/功能失效）
→ 风险链：HR-08=高 → risk floor=高 → handoff_required=true
→ 生成：本地模板输出质量缺陷类转人工文案（含下一步：提供订单号+照片凭证）
→ 响应 risk_level=高、answer_mode=fallback、answer 不含任何 HR 编号
```

## 五、指标名词解释

- **Hit@1**：期望片段排第一的比例（答案用 Top1 生成时最关键）；
- **Hit@3 / union Hit@3**：期望片段集合（可多答案）在 Top3 内至少出现一个的比例；
- **MRR**：第一个命中片段排名倒数的均值（排名敏感的总体质量）；
- **Rule Recall@3**：风险规则类用例中，期望规则片段全部进入 Top3 的比例（安全类检索的底线指标）。

## 六、为什么开发集 100% 但 blind 较低？

开发集用于迭代，评测循环（发现失败→改门控/词表→重跑）天然会向开发集的**表达方式**收敛。盲测题是全新措辞（禁止同义改写、禁止按关键词表反向拼题），考察的是对"没见过的说法"的泛化。开发集 Hit@1 90.2% → 盲测 54.5%，落差集中在：门控对旧句式过拟合、风险意图词表按开发集措辞强化、FAQ 语义竞争未真正解决。

## 七、如何判断过拟合

三个信号（本项目全部命中）：

1. 开发集/验证集接近满分，盲测同一指标大幅下降（>30 个百分点）；
2. 失败案例集中在"表达方式变了但语义没变"的问题上（盲测 HR-07 新表述漏检）；
3. 修复历史只对评测集指标有效、对失败根因（语义竞争）无效。

对策不是继续调盲测，而是：扩充失败模式覆盖的**全新**开发集、重建盲测集再验收。

## 八、为什么不继续针对 blind 修复

三个原因：

1. **纪律自洽**：盲测只执行一次是事先冻结的规则，事后重跑等于把盲测变成开发集，之前所有"冻结+一次性执行"的工程努力全部作废；
2. **科学性**：针对已知失败案例修复后重跑同一套题，提升的是记忆不是泛化，指标会系统性虚高；
3. **价值排序**：失败清单（7 类模式）作为后续版本的需求输入，比一个刷出来的好看数字更有工程价值。

## 九、AI 生成代码比例如何诚实说明

标准回答："代码大部分由 AI 智能体在我的分阶段指令下生成，但**架构决策、业务口径、评测纪律和每阶段验收是我做的**。而且我保留了 AI 出错的完整记录——比如风险等级排序反序、否定守卫漏判、评测器字段误报，都是我逐轮验收时拦下来的。所以这个项目展示的不只是代码，是'如何让 AI 产出变得可验收、可审计'的流程。"

## 十、面试官可能追问的 20 个问题及答案

1. **问：为什么 RRF 而不是加权分数融合？**
   答：RRF 只用排名不用分数，避免了关键词 BM25 分数与余弦相似度不可比的问题；K=60 是标准平滑常数。为避免"调参过拟合"，权重从头到尾冻结未调。

2. **问：RRF_K=60 是拍脑袋吗？**
   答：是文献常用值，我们没有做 K 的网格搜索——因为任何针对评测集调参都会污染评测。这是"损失一点最优性换评测纯净度"的取舍。

3. **问：bge-small 而不是 large？**
   答：本地 CPU 推理延迟要求（P95<100ms）和资源约束下的选择；small 对该规模知识库（33 片段）够用，盲测瓶颈不在 embedding 质量而在意图/门控层。

4. **问：门控会不会把该答的问题拦掉？**
   答：会，盲测有 1 条 unsupported→irrelevant 误拦和 1 条过度门控。门控阈值是查准/查全的权衡，生产上应加"低置信度→人工"的第三出口。

5. **问：unsupported 误放行 20% 怎么改？**
   答：两例都是未知商品串答。方向是能力目录驱动的反向校验（问题里的商品实体不在目录→直接拦截），而不只是提高相似度阈值——阈值提高会同时伤 supported 召回。

6. **问：风险下限怎么实现"模型不能降低"？**
   答：生成后取 `max(模型风险, 检索风险下限, 本地规则风险)`，等级映射唯一定义在 risk_levels.py。曾经有处 adapter 的顺序数组写反导致取了最低风险——这正是统一公共定义的价值。

7. **问：否定承诺怎么处理？**
   答：检测承诺动词前缀的否定语境（"能不能保证"是询问不是要求；"我知道你不能保证"是让步）。盲测暴露了它对"没想让你们打包票"仍失效——词表法的天花板，需要小模型意图分类。

8. **问：为什么订单不进向量库？**（见 PORTFOLIO.md 第 3 节）——正确性（精确匹配）、隐私（防相似度召回他人订单）、事实性（模板可控不编造）。

9. **问：如何防止订单串单？**
   答：12 位精确匹配 + 他人订单语境转人工 + 不完整单号只提示补全不猜单。盲测 7/8 正确，唯一失败是"尾号 003"指代不识别（意图覆盖问题）。

10. **问：内部泄漏 0 怎么保证的？**
    答：四层防线（数据拆分/提示词禁令/正则校验重试/评测扫描），且评测扫描词表独立于实现（从评审角度反向构造）。

11. **问：DeepSeek 挂了用户体验如何？**
    答：本地降级模板，回答略生硬但信息正确、安全约束同等生效；盲测全部 80 条就是在 DeepSeek 0 次调用下完成的——降级链路是被完整评测过的主路径，不是应急补丁。

12. **问：为什么 answer_mode 有 deterministic/fallback 两种本地模式？**
    答：deterministic 是确定性场景（如订单查询、固定话术）的正常模式，fallback 是 DeepSeek 失败后的降级。评测器漏把 deterministic 加入白名单是它的口径缺陷，已在报告披露。

13. **问：评测器自己有 bug，指标还可信吗？**
    答：三处口径缺陷（message 字段、deterministic 白名单、订单分支 Rule Recall 失真）都已定位并披露修正口径（API 契约 0/10→修正 8/10），且原始结果文件未改——可信度来自可审计的披露，不是来自"没错过"。

14. **问：80 条盲测样本量够吗？**
    答：不够下强结论，够下方向性结论。±5% 的波动在这个量级是正常的。生产上应该建立"固定开发集 + 定期轮换盲测集"的持续评测管线。

15. **问：为什么不微调一个小模型做风险分类？**
    答：数据量（8 类规则、几百条语料）和工程成本不匹配当前阶段；规则+词表是可解释的 baseline，先用评测证明它的边界（盲测漏检 4 条），再决定是否上模型。

16. **问：多轮对话为什么不做？**
    答：会引入状态管理、指代消解和上下文安全等新变量，与本项目"单轮问答的检索/安全/评测纪律"主线分离；盲测里"尾号 003"的失败恰好说明指代消解需要单独设计。

17. **问：HR-08 片段召回 0% 但你说风险意图正确，矛盾吗？**
    答：不矛盾——那是两个口径。风险触发走结构化意图检测（不依赖片段召回），所以"转人工"行为正确；但期望的规则知识片段没进 Top3，影响的是答案的信息含量。这暴露了"意图识别"与"知识检索"两条链路的独立性。

18. **问：如果只有一周，你优先修什么？**
    答：B 层 FAQ 串答（生成前加"检索片段与意图一致性校验"）、未知商品反向校验、订单尾号指代——三个都是评测器能明确归因、修复后可用全新小样本验证的问题。

19. **问：这个项目最难的决策是什么？**
    答：盲测 Hit@1 54.5% 后"停手归档"。继续修复的诱惑很大，但会推翻整套评测纪律。选择如实发布失败，是因为作品集的价值在工程判断力，不在指标好看。

20. **问：和直接用 LangChain/RAG 框架比，自研的价值在哪？**
    答：框架解决的是"跑起来"，这个项目的核心难点——风险下限不可被模型覆盖、订单不进向量库、盲测一次性纪律、哈希冻结链——都是框架不提供的治理层。自研让每个环节可解释、可审计。
